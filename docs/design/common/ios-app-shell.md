# iOS App Shell

## Purpose

Orbit is a Next.js progressive web app. On an iPhone it can be added to the Home Screen and it
works, but it is a web page: it can reach no native iOS framework. The iOS app shell is a thin
Capacitor wrapper that puts the same web app inside a signed app bundle, which is the only place
ActivityKit, APNs, Face ID or HealthKit can be called from at all.

The shell adds no product surface of its own. It hosts a `WKWebView` pointed at the deployed site
and registers native plugins; every screen the user sees is the same web app the browser shows.

Command IDs: `ios-sync`, `ios-open` (see `AGENTS.md`).

## What Lives Where

| Path                             | What it is                                                         |
| -------------------------------- | ------------------------------------------------------------------ |
| `capacitor.config.ts`            | The file Capacitor reads; delegates to the module below            |
| `native/ios/capacitor-config.ts` | Every decision the config encodes, as a tested function of the env |
| `native/ios/www/index.html`      | The only page inside the bundle: shown when the origin is offline  |
| `ios/`                           | The generated Xcode project, committed                             |
| `.github/workflows/ios.yml`      | Builds, signs and uploads it on a macOS runner                     |

`ios/` is generated by `npx cap add ios` and regenerated by deleting it and running that again.
Treat it as output — but it carries two hand edits that a regenerate would drop, and
`native/ios/xcode-project.test.ts` fails if either goes missing:

- the App Transport Security exception described below, and
- `App.xcodeproj/xcshareddata/xcschemes/App.xcscheme`. The Capacitor template ships no scheme;
  Xcode writes one on first open into `xcuserdata`, which is gitignored, so the project would build
  on the machine that opened it and nowhere else. `xcodebuild` on a fresh runner fails with "does
  not contain a scheme named App" before compiling anything.

## Identity

The bundle identifier is `com.podreshetnikov.orbit`, registered to the owner's Apple Developer team
and spelled once, in `native/ios/capacitor-config.ts`.

It is not a name that can be changed later. `iosBundleIdentifiers()` derives the App Group, the
keychain access group and the Live Activity APNs topic from it, and a push token is issued against
the topic that existed when the device registered. Changing the identifier orphans every stored
token, and the failure mode is silence — pushes are accepted and never delivered.

## Loading The Deployed Site

`server.url` points at `https://private-orbit.vercel.app`. The app ships no copy of the web app, so
a web deploy reaches every installed app immediately, with no new signed build and no new TestFlight
upload. The cost is that the app needs connectivity to start; it is a Supabase client end to end and
can do nothing useful offline today, so this is not a real loss. When the origin cannot be reached,
`server.errorPath` shows `native/ios/www/index.html` instead of a blank web view.

To test against a local dev server, point the shell at the machine's LAN address — the phone cannot
reach the Mac's `localhost`:

```sh
ORBIT_IOS_SERVER_URL=http://192.168.1.42:3000 just ios-sync
```

The variable is read when the config is evaluated on the Mac, so whatever it held at sync time is
baked into the project until the next sync. Run `just ios-sync` with it unset to go back to
production. `native/ios/capacitor-config.ts` refuses a plaintext `http` override against anything
but a loopback or private-network address, so a forgotten scheme cannot ship an app whose traffic is
readable on the wire.

Two settings make that override work, and they are easy to confuse:

- `server.cleartext` is an **Android** setting, and is derived from the scheme of the resolved URL.
- On **iOS** it is App Transport Security that refuses plaintext http. `ios/App/App/Info.plist`
  carries `NSAllowsLocalNetworking`, which permits it for local addresses only and leaves ATS
  enforced for the public internet, plus the `NSLocalNetworkUsageDescription` iOS shows in the local
  network permission prompt. This is the one hand edit inside `ios/`; reapply it after a regenerate.

## Prerequisites For Building

- An **Apple Developer Program membership** ($99/year). This one is unavoidable: without it a build
  can still be side-loaded from Xcode, but the provisioning profile expires after seven days and
  TestFlight is unavailable. Enrolment is done from an iPhone or iPad through the Apple Developer
  app; a Mac is not needed for it.
- A **physical iPhone**. The Live Activities this shell exists to unblock do not render in the
  Simulator, and the phone doubles as the TestFlight install target.
- A **Mac with Xcode** is _optional_. See below.

CocoaPods is **not** required. Capacitor 8 generates the project against Swift Package Manager, so
there is no `Podfile` and no `pod install` step, and `npx cap add ios` runs on any platform.

### Why a Mac is optional

Everything that genuinely needs macOS — `xcodebuild`, signing, the upload — happens on a
GitHub-hosted macOS runner in `.github/workflows/ios.yml`. Orbit is a public repository, and macOS
minutes are free and unmetered on public repositories, so this costs nothing.

The two remaining reasons a Mac used to be mandatory both have answers:

- **Creating the signing certificate** normally means generating a signing request in Keychain
  Access. Instead the workflow passes an App Store Connect API key to `xcodebuild
-allowProvisioningUpdates`, and Xcode creates the certificate and the provisioning profile
  against the account itself. Nothing is generated by hand and no `.p12` is carried around.
- **Running on a device** normally means a cable and Xcode's Run button. Instead the build reaches
  the phone through TestFlight, exactly the way it reaches anyone else's phone.

What a Mac still buys is **Safari Web Inspector**, which is the only supported way to inspect the
web view running on a device. If the web app misbehaves inside the shell but not in Safari on the
same phone, that is the point at which renting a Mac for a day earns its cost.

## Building In CI

`.github/workflows/ios.yml` has two jobs, split by what they require.

**`build`** compiles the project with `CODE_SIGNING_ALLOWED=NO`. It needs no Apple account and no
secrets, and runs on every pull request that touches `ios/`, `native/`, `capacitor.config.ts` or
the lockfile. It is the only gate in this repository that proves the Xcode project compiles at all
— the unit tests around the shell never invoke a compiler. It also fails if `npx cap sync ios`
changes a committed file, which catches a Capacitor upgrade that nobody re-synced.

**`testflight`** archives, signs, exports and uploads. It runs only on a deliberate
`workflow_dispatch` with the `upload_to_testflight` input set, because it spends the Apple account
and because a TestFlight upload is not something to do on every push. The build number comes from
the workflow run number, since App Store Connect refuses a build number it has already seen.

It needs four values, set once in the repository settings:

| Name                       | Kind       | Where it comes from                                        |
| -------------------------- | ---------- | ---------------------------------------------------------- |
| `APPSTORE_ISSUER_ID`       | variable   | App Store Connect → Users and Access → Integrations → Keys |
| `APPSTORE_API_KEY_ID`      | variable   | the key's id, on the same screen                           |
| `APPSTORE_TEAM_ID`         | variable   | Apple Developer → Membership                               |
| `APPSTORE_API_PRIVATE_KEY` | **secret** | the contents of the `AuthKey_*.p8` file, downloadable once |

The API key must carry the **App Manager** role. A lesser role can upload but cannot create the
certificate, so `-allowProvisioningUpdates` fails at the archive step rather than at the upload.

The upload declares `uses-non-exempt-encryption: false`. That is an export-compliance statement:
the app's only cryptography is the HTTPS it speaks to the deployed origin, which is exempt. Without
it every build sits in App Store Connect waiting for the question to be answered by hand.

## Running On A Device

The Mac-free route is simply to run the `testflight` job and install the build from TestFlight on
your own phone, the same way any other tester will. What follows is the Xcode route, which is
faster to iterate on when a Mac is at hand.

1. `just ios-sync` — copies web assets and plugin packages into `ios/`.
2. `just ios-open` — opens `ios/App/App.xcodeproj` in Xcode.
3. Select the **App** target, then **Signing & Capabilities**, and pick the developer team. Leave
   _Automatically manage signing_ on; Xcode registers the device and issues the profile.
4. Select the connected iPhone as the run destination and press Run.
5. The app launches on the login screen the browser shows. Sign in and reach `/health/medications`.

Trust the developer certificate on the phone the first time, under Settings → General → VPN & Device
Management.

## Distribution Through TestFlight

Run the **iOS** workflow from the Actions tab with `upload_to_testflight` checked. It archives,
signs, exports and uploads, and with `wait-for-processing` it does not report success until App
Store Connect has finished processing the build — so a green job means the build is really there.

From a Mac the same thing is done by hand: set the run destination to **Any iOS Device (arm64)**,
Product → Archive, then Distribute App → App Store Connect → Upload in the Organizer window.

Either way, add the build to TestFlight in App Store Connect afterwards.

For family use, external testing with a public link is the least friction: testers install the
TestFlight app and follow a URL, with no Apple ID added to the developer team and no Mac involved.
The first build for external testers passes a Beta App Review, usually about a day and lighter than
full App Store review.

**TestFlight builds expire ninety days after upload.** After that the link stops installing for new
testers and a fresh build has to be uploaded, whether or not the web app changed.

## What CI Can And Cannot Check

Two layers, and it is worth knowing which one a given failure comes from.

`native/ios/*.test.ts` runs in the `node` unit lane on Linux, in seconds, on every change. It covers
what needs no compiler: the resolved origin and its validation, the derived identifiers, the
presence of the `index.html` `cap sync` refuses to run without, and the hand edits inside `ios/`
that a regenerate would drop.

The `build` job in `.github/workflows/ios.yml` compiles the project on macOS. It is what proves the
Xcode project is real rather than merely well-formed, and it is where a broken scheme, a Swift
package that will not resolve, or a Capacitor upgrade that nobody re-synced shows up.

What no gate covers: **that the app works on a phone.** Nothing here launches a web view, signs in,
or renders anything. A green pipeline means a signed bundle reached TestFlight, not that the
product behaves — that still takes a person, a device and a look.
